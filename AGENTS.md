## Code style guidelines

These are mandatory best practices for all generated and edited code:

- Class and method comments: do not add comments inside method bodies. Only service interface methods may be documented.
- Language: all source code and comments must be written in English.
- Method length: a method must not exceed 20 lines of code.
- Line length: maximum 100 columns per line.
- Indentation: 2 spaces; for wrapped lines use 4 spaces indentation.
- Unused imports: remove unused imports whenever code is added or modified.
- Naming conventions:
  - Methods in lowerCamelCase with descriptive names.
  - Class names start with uppercase and must be simple and descriptive; acronyms only allowed for Dto, enum, impl, mapper, config.
  - Variables in lowerCamelCase; static constants in UPPER_SNAKE_CASE.
- Prefer modern Java features available in the target version () where appropriate, such as switch expressions, records, and text blocks when supported.
- Prefer functional programming patterns when they improve clarity.
 - Strict copy blocks: when a code block includes a line with `# bloque_estricto_a_copiar`, the agent must copy the entire block exactly as shown, without customization, modification, or summarization.

### Class naming by responsibility
- Controller: `FooController.java` (implements OpenAPI interfaces)
- Service: `FooService.java` (interface only)
- Repository: `FooRepository.java`
- Domain model: `Foo.java` (business objects or database entities)
- Utility: `FooUtil.java` (static helpers only)
- Helper: `FooHelper.java` (non-static helpers)
- Exception: `FooException.java` (custom exceptions)
- Configuration: `Foo.config.java` (configuration only)
- Mapper: `FooMapper.java` (domain ↔ OpenAPI models via MapStruct)
- Enum: `FooEnum.java`
- Service implementation: `FooServiceImpl.java` (implements service interfaces)

### Lombok usage
- Use Lombok to generate boilerplate. Do not write manual getters, setters, constructors, or builders unless strictly necessary.
- Annotate domain models, DTOs, and configuration beans with Lombok annotations as appropriate:
  - `@Getter` and `@Setter` to generate accessors.
  - `@Builder(toBuilder = true)` to construct immutable-style objects with copy semantics.
  - Consider `@AllArgsConstructor`, `@NoArgsConstructor`, and `@With` when needed.
- Ensure annotation processing is enabled in your IDE.

Example:

```java
// bloque_estricto_a_copiar
import lombok.Builder;
import lombok.Getter;
import lombok.Setter;

@Getter
@Setter
@Builder(toBuilder = true)
public class SampleDto {
  private String id;
  private String name;
}
```

## Commit Message Generation

### Commits Messages
Commit messages must be clear, informative, and professional to aid readability and project tracking.

### Objective
Follow the Conventional Commits specification strictly for commit messages.

### Structure
The commit message must follow this structure:

```text
<type> [optional scope]: <description>

[optional body]

[optional footer(s)]
```

### Guidelines
1. Title: Start with a concise, informative title.
2. Type: Choose an appropriate type (`feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `ci`, `perf`, `build`, `revert`, `iac`).
   - Use `feat` for new features (maps to PATCH in SemVer).
   - Use `fix` for bug fixes (maps to MINOR in SemVer).
   - Use `docs` for documentation changes.
   - Use `style` for changes that do not affect meaning (formatting, whitespace).
   - Use `refactor` for code changes that neither fix a bug nor add a feature.
   - Use `test` for adding or correcting tests.
   - Use `chore` for build processes or auxiliary tools.
   - Use `ci` for CI configuration and scripts.
   - Use `perf` for performance improvements.
   - Use `build` for build system or external dependencies.
   - Use `revert` for reverting a previous commit.
   - Use `iac` for Infrastructure as Code changes.
3. Scope: Optionally specify the impacted module, resource, or feature.
4. Description: Write a concise, informative description in the header; use backticks for code or specific terms.
5. Body: Provide additional details when necessary:
   - Use bullet points (*) for clarity.
   - Describe motivation, context, and technical details as needed.
6. Footers: Use standard trailers; for breaking changes include a footer:
   - BREAKING CHANGE: <description>
   - A commit with a `BREAKING CHANGE` footer, or a `!` after type/scope, indicates a breaking API change (maps to MAJOR in SemVer). Breaking changes may appear with any type.

### Importance
These instructions are important because they are critical to organizational standards and consistent versioning.
